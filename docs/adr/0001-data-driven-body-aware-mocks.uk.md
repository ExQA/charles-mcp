# ADR-0001: Моки на даних з маршрутизацією за тілом запиту

**Статус:** Прийнято
**Дата:** 2026-09-12
**Хто затверджує:** власник форку charles-mcp, QA-команда мобільних застосунків, служба безпеки (щодо зберігання знятих даних)

> English version: [0001-data-driven-body-aware-mocks.md](0001-data-driven-body-aware-mocks.md)

## Контекст

Сценарій QA:
1. Charles записує справжній трафік мобільного застосунку.
2. Агент через MCP читає сесію.
3. Користувач каже, які дані у відповіді або в запиті треба підмінити.
4. Charles віддає застосунку підмінену відповідь.

Що заважає:

- **Map Local обирає файл лише за URL.** Query string і метод він ігнорує (перевірено на Charles 5.2.1). Багато API надсилають усі операції POST-запитом на один URL, а операцію визначає поле тіла, наприклад `{"action": "init"}` або `{"action": "get_cards"}`. Для таких ендпоінтів Map Local може підмінити або всі варіанти одразу, або жодного.
- **Map Local завжди відповідає статусом 200**, тому помилки 4xx/5xx через нього не перевірити.
- **Правила Charles не можна міняти на льоту.** Web Interface вміє лише вмикати й вимикати інструменти, а конфіг Charles під час виходу перезаписує з пам'яті (перевірено 2026-09-10). Будь-яка правка файлу при запущеному Charles втрачається, навіть після «перезапуску».

## Рішення

Маршрути, де відповідь залежить від тіла запиту, йдуть через **локальний диспетчер**, а правила для нього — **дані в каталозі моків**, не код.

```
Застосунок ──► Charles ──(Map Remote, preserve host header)──► диспетчер 127.0.0.1:18080
                                                                   │
                                     правило підійшло, fixture ────┼──► відповідь з файлу (будь-який статус)
                                     правило підійшло, patch ──────┼──► справжній сервер ─► правка відповіді
                                     правила немає ────────────────┴──► справжній сервер без змін
```

Сховище поза репозиторієм (`CHARLES_MOCK_DIR`, за замовчуванням `~/charles-mocks`):

```
_rules/routes.json              маршрути: хост або шаблон домену, шаблони шляхів, схема, порт, перевірка TLS
_rules/_any/<rule_id>.json      правила на будь-який хост (`*`) або шаблон домену
_rules/<host>/<rule_id>.json    правила лише для одного хоста
<rule_id>.body                  фікстура (вихідна знята відповідь) поруч із правилом, лише для fixture
_archive/                       попередні версії; нічого не видаляється
```

Правило підходить до запиту, якщо збігаються метод, шлях, підмножина query і заголовків, а також значення за JSON Pointer у тілі (JSON або form), наприклад `{"/action": "init"}`. Якщо підходить кілька правил, обирається правило з більшим `priority`, потім конкретніше, потім за `id`.

Режими:
- **`patch`** (за замовчуванням). Запит іде на справжній сервер, за потреби з правками тіла запиту. У справжньої відповіді змінюються лише вказані поля. Дані лишаються свіжими, а мок вузький і зрозумілий.
- **`fixture`**. Відповідь береться зі знятого файлу, до неї застосовуються правки, статус будь-який (наприклад 500). Справжній сервер не викликається.

**Масштаб: багато шляхів, action і хостів.** У справжньому проєкті шляхів і action десятки, а те саме API працює на кількох хостах (dev, stage тощо). Тому:
- маршрут заводиться **один раз на домен**: `https://*.example.com/api/*` → диспетчер, з порожнім шляхом призначення, тож Charles зберігає вихідний шлях. Більше Charles не чіпаємо, все інше — дані;
- правило за замовчуванням діє **на будь-якому хості маршруту** (`host: "*"`). Можна звузити до шаблону або одного хоста, і правило для точного хоста перемагає загальне;
- агент починає з **огляду всієї сесії** (метод × хост × шлях × `action`), а не одного URL;
- повторні правки одного варіанта **накопичуються в його правилі**, правка того самого поля замінює попередню.

Агент працює так:
1. `mock_route_setup` — один раз на домен.
2. `mock_discover_variants` — уся сесія: метод × хост × шлях × `action`.
3. `mock_rule_create_from_entry` — правило (або доповнення правила) на кожен варіант, який назвав користувач.
4. `mock_dispatcher` — запустити диспетчер.
5. Перевірити результат за заголовком `X-Charles-MCP-Rule`.

Map Local-моки (`mock_*` без `rule`) лишаються для простих GET і унікальних URL.

## Що Charles дозволяє за офіційною документацією

Перевірено за [документацією Charles](https://www.charlesproxy.com/documentation/) і за класами встановленого Charles 5.2.1 (2026-09-12).

| Спосіб | Що можна | Міняє правила на льоту? |
|---|---|---|
| [Web Interface](https://www.charlesproxy.com/documentation/using-charles/web-interface/) (`http://control.charles`) | Вмикати й вимикати інструменти, пресети сповільнення, запис; очищати й експортувати сесію; закрити Charles. Документація сама пропонує автоматизувати його як вебсервіс | Ні: лише ввімк/вимк інструмента цілком |
| UI: Tools → Map Remote / Map Local / Rewrite | Будь-які правила; зміни застосовуються одразу після **Done** | Так, але руками |
| UI: Import у вікні інструмента, Tools → Import/Export Settings | Завантажити правила з XML-файлу | Так, але руками (два кліки) |
| Файл конфіга (`com.xk72.charles.config`) | Будь-які правила | Ні: читається лише під час старту і перезаписується з пам'яті під час виходу |
| [Командний рядок](https://www.charlesproxy.com/documentation/using-charles/command-line-options/): `-config`, `-headless`, `-throttling`, `--debug` | Запуск з іншим конфігом, без GUI, зі сповільненням | Ні: лише під час запуску |
| [CLI-утиліти](https://www.charlesproxy.com/documentation/tools/command-line-tools/): `convert`, `ssl`, `filter` (5.2) | Робота зі збереженими сесіями та сертифікатами | Ні |
| [Breakpoints](https://www.charlesproxy.com/documentation/proxying/breakpoints/) | Правка запиту або відповіді вручну | Так, але блокує запит до дії людини; автоматизації немає |

Що це означає для підміни даних:

- **[Map Remote](https://www.charlesproxy.com/documentation/tools/map-remote/)** зіставляє за protocol, host, port і path з підтримкою wildcard. «Якщо в призначенні не вказано шлях, шлях URL не змінюється». Вміє HTTP↔HTTPS, «Preserve host header», а в 5.2.1 з'явився «Preserve base path». Умов за тілом запиту немає.
- **[Rewrite](https://www.charlesproxy.com/documentation/tools/rewrite/)** вміє правила для заголовків, URL, query, тіла і статусу відповіді, Perl-регулярні вирази з групами `$1`, `$2`, роботу із запитом, відповіддю або обома. Умова — лише location (protocol, host, port, path), **не тіло запиту**. Тому регулярним виразом можна змінити поле в усіх відповідях URL, але не лише для `action=init`.
- **Правил з умовою за тілом запиту в Charles немає в жодному інструменті**, API і скриптів теж. Розрізняти `action` можна лише ззовні Charles, звідси й диспетчер.
- **«На льоту» без рук** у Charles змінюється лише одне: вміст, на який вказує статичне правило. Це файли Map Local і відповіді диспетчера за Map Remote. Обидва механізми цього форку побудовані на цьому.

Формат серіалізації Map Remote у Charles 5.2.1 (`MapTool.MapConfiguration.MapMapping`: `sourceLocation`, `destLocation`, `enabled`, `preserveHostHeader`, `preserveBasePath`, елемент `mapMapping`) збігається з тим, що пише `apply_map_remote_route`.

## Розглянуті варіанти

### Варіант A: лише Map Local (поточне рішення)

| Параметр | Оцінка |
|---|---|
| Складність | Низька |
| Вартість | Немає |
| Масштабованість | Добра для унікальних URL, **нуль** для «один URL — багато action» |
| Знайомість команді | Висока |

**Плюси:** працює без агента і без додаткових процесів, файл = мок.
**Мінуси:** не розрізняє тіло запиту, завжди статус 200, не вміє правити запит.

### Варіант B: правила Rewrite у Charles за регулярним виразом тіла відповіді

| Параметр | Оцінка |
|---|---|
| Складність | Низька |
| Вартість | Немає |
| Масштабованість | Погана |
| Знайомість команді | Середня |

**Плюси:** без окремого процесу.
**Мінуси:** Rewrite не вміє умову за тілом *запиту*, тому за `action` не розрізняє. Регулярний вираз по JSON крихкий, правило діє на весь хост, а міняти правила можна лише при закритому Charles.

### Варіант C: універсальний диспетчер + правила-дані (обрано)

| Параметр | Оцінка |
|---|---|
| Складність | Середня: близько 600 рядків коду і 39 тестів |
| Вартість | Локальний процес на `127.0.0.1` |
| Масштабованість | Будь-які хости й ендпоінти без зміни коду |
| Знайомість команді | Середня: JSON Pointer і JSON-файли |

**Плюси:** розрізняє тіло, query і заголовки; править і запит, і відповідь; будь-який статус; правила міняються на льоту (читаються з диска на кожен запит); дані ніколи не потрапляють у репозиторій.
**Мінуси:** доки маршрут заведений у Charles, диспетчер має працювати, інакше запити на цей URL падають. Map Remote налаштовується один раз на URL: вручну в UI Charles будь-коли або автоматично (`apply=true`) лише при закритому Charles. Вихідний HTTPS іде від диспетчера, тому для внутрішніх CA може знадобитися `verify_tls=false`.

### Варіант D: замінити Charles на mitmproxy з аддонами

| Параметр | Оцінка |
|---|---|
| Складність | Висока: зміна інструмента |
| Вартість | Перенавчання команди, нове налаштування пристроїв і сертифікатів |
| Масштабованість | Відмінна |
| Знайомість команді | Низька |

**Плюси:** програмований проксі, умови за тілом з коробки.
**Мінуси:** виходить за межі задачі: команда, ліцензії та всі напрацювання зав'язані на Charles.

## Аналіз компромісів

Вирішальне питання — **де живуть дані моків**. У коді вони потрапили б у git і релізи, а конфіг Charles (B) не можна міняти при запущеному застосунку. C переносить дані в каталог користувача, який не комітиться, і лишає в Charles одне статичне правило на URL.

Друге питання — **що робити із запитом без відповідного правила**. C пересилає такий запит на справжній сервер без змін, тому мокається рівно те, що попросив користувач, а решта застосунку працює як звичайно.

Ціна C — окремий процес. Це прийнятно: диспетчер запускається однією командою агента (`mock_dispatcher`) або окремо (`charles-mcp-dispatcher`), а при його зупинці достатньо вимкнути правило Map Remote.

## Наслідки

**Що стає простіше:**
- мокати варіанти одного URL за полем тіла, query або заголовком;
- перевіряти помилки (будь-який статус) і граничні дані (патч одного поля у справжній відповіді);
- додавати нові ендпоінти без коду і релізу;
- перевіряти, що відповідь прийшла з мока: заголовок `X-Charles-MCP-Rule`.

**Що стає складніше:**
- стежити, щоб диспетчер працював, доки маршрут заведений;
- маршрут на весь хост (`/*`) пропускає через диспетчер статику і WebSocket: завантаження буферизуються, WebSocket не підтримується. Тому маршрут краще обмежувати префіксом API (`/api/*`);
- налаштовувати Map Remote: один раз на URL, вручну в UI або через `apply=true` при закритому Charles;
- зберігати `~/charles-mocks`: там зняті справжні відповіді, їх не можна комітити й пересилати.

**До чого повернутися:**
- ~~перевірити на живому Charles мапінг із шаблоном хоста і порожнім шляхом призначення~~ — **перевірено 2026-09-12 на Charles 5.2.1**: `http://*.example.com/api/*` спіймав `www.example.com`, шляхи `/api/wallet` і `/api/deep/other/path` дійшли до диспетчера без змін, `/index.html` поза префіксом не мапився, а Charles під час виходу зберіг правило з шаблоном;
- ~~перевірити на живому Charles, що Map Remote з «preserve host header» передає вихідний `Host`~~ — **перевірено 2026-09-12 на Charles 5.2.1**: правило, записане `apply_map_remote_route` при закритому Charles, завантажилося під час старту; через проксі Charles `action=init` (JSON і form) отримав відповідь правила, а `action=transactions` пішов на справжній `example.com` з `X-Charles-MCP-Rule: passthrough`. Лишилося перевірити з телефона по HTTPS (потрібні SSL Proxying і сертифікат);
- режим `restart_charles`: безпечно закрити Charles через `/quit`, записати правила і запустити знову, з явною згодою користувача, бо втрачається незбережена сесія;
- маскування персональних даних у фікстурах під час створення правила.
