# charles-mcp — посібник для агента

> Переклад для людей. Агент отримує англійський оригінал від самого MCP-сервера: короткі правила — у полі `instructions` під час підключення, повний посібник — ресурс `charles-mcp://agent-guide` (файл [charles_mcp/resources/agent_guide.md](../charles_mcp/resources/agent_guide.md)). За розбіжності вірний оригінал.

Усе, що потрібно агенту для правильної роботи із сервером: модель роботи, обов'язкові правила, всі інструменти, основні сценарії, особливості Charles і діагностика.

## 1. Що це за сервер

- **Джерело істини — Charles Proxy.** Трафік застосунку йде через Charles (телефон, симулятор або цей комп'ютер). Сервер читає Charles через Web Interface (`http://control.charles`, через проксі Charles) і сам трафік не перехоплює.
- **Кожен live-запит вивантажує всю сесію Charles.** Вартість зростає з розміром сесії. Якщо в Charles увімкнений проксі macOS, він пише *весь* трафік комп'ютера, і сесія росте швидко.
- **Моки — це дані, а не код.** Map Local віддає файли з `~/charles-mocks/<host>/`, локальний диспетчер — правила з `~/charles-mocks/_rules/`. У Charles зберігається лише одне статичне правило на хост або домен.
- **Вивід сирий.** Результати інструментів містять справжні заголовки, токени, cookie і тіла, включно з персональними та платіжними даними. Усе прочитане вважайте чутливим.

## 2. Обов'язкові правила

1. **Ніколи не очищайте сесію Charles користувача** без його явного прохання. `start_live_capture` за замовчуванням підхоплює поточну сесію; `reset_session=true` — лише на явне прохання: помилкову очистку не скасувати.
2. **Ніколи не пишіть конфіг Charles, доки він запущений.** Charles під час виходу перезаписує конфіг з пам'яті, і правка втрачається. `apply=true` відмовляється працювати, доки відкритий порт проксі, — не обходьте це.
3. **Ніколи не закривайте і не перезапускайте Charles без згоди користувача.** Під час виходу втрачається незбережена сесія. Спершу попросіть зберегти її (File → Save Session).
4. **Ніколи не викликайте `reset_environment`**, якщо користувач не попросив саме це. Він закриває Charles, перезаписує конфіг з бекапа і видаляє збережені записи.
5. **Не повторюйте запити і не пересилайте змінені запити на прод без згоди.** `reverse_replay_entry` і правила диспетчера в режимі patch надсилають справжні запити зі справжніми обліковими даними на справжні сервери.
6. **Ніколи не записуйте зняті значення в код, тести, коміти і спільні файли** і не пропонуйте комітити `~/charles-mocks`. Якщо мок треба передати, використовуйте синтетичні дані.
7. **Не повторюйте користувачу секрети** (токени, паролі, повні номери карток) без потреби; називайте їх за іменем поля.
8. **Ніколи не перебудовуйте мокнуту відповідь.** Зберігайте зняту форму: порядок ключів, вкладеність, обгортки, назви полів, порядок масивів і скалярні типи (`0` — не `0.0`, `"1"` — не `1`). Будуйте мок зі знятого запису і міняйте лише названі користувачем поля; ніколи не набирайте відповідь з пам'яті. Застосунки розбирають суворіше, ніж вимагає JSON, і перебудоване тіло ламається, хоча відповідь і 200 (розділ 6.5).
9. **Пам'ятайте, що Charles завантажує мапінги Map Remote лише під час запуску.** Після `apply=true` користувач має запустити Charles; доти мапінг не діє, хай яким правильним виглядає файл конфіга. Якщо маршрутизований трафік не доходить до диспетчера, спершу виконайте `mock_dispatcher(action="verify")`, а вже потім підозрюйте правило.
10. **Лишайте оточення таким, яким воно було:** наприкінці сценарію видаліть або вимкніть додані моки, зупиніть запущений диспетчер і скажіть, які правила в Charles лишилися.

## 3. Перші перевірки

1. `charles_status` — чи доступний Charles, чи правильні облікові дані Web Interface, чи є активне захоплення. Дійте за його `recommended_next_action`.
2. HTTPS: у Charles має бути ввімкнений **SSL Proxying** для хостів API, а пристрій має довіряти сертифікату Charles. Без цього Charles бачить лише тунель, шлях невідомий, і правила за шляхом не спрацьовують.
3. Розмір сесії: якщо вивантаження повільне, запропонуйте очистити сесію перед сценарієм, а якщо тестується лише телефон — вимкнути в Charles Proxy → macOS Proxy.

## 6. Основний сценарій: підміна даних зі справжньої сесії

### 6.1 Вибір механізму

- GET, унікальний URL, статус 200 підходить → **Map Local** (5.6).
- POST з полем операції (`action`), кілька шляхів або хостів, статуси помилок, правка запиту → **правила диспетчера** (5.7).

### 6.2 Налаштування один раз на домен

1. `mock_route_setup(host="*.example.com", path="/api/*")` без `apply` → покажіть користувачу кроки налаштування Map Remote **або** виконайте розділ 7 і викличте з `apply=true`.
2. Переконайтеся, що SSL Proxying покриває домен.

### 6.3 На кожну сесію

1. **Прочитати сесію.** `start_live_capture()` бачить усе, що вже записано в Charles. Для нового сценарію користувач проходить його після старту, нові записи потрапляють у те саме захоплення.
2. **Огляд.** `mock_discover_variants(source="live", capture_id, host_contains=...)`. Покажіть користувачу варіанти (метод, шлях, `action`, кількість, статус) і спитайте, що міняти, якщо він ще не сказав.
3. **На кожну правку** візьміть приклад `entry_id` цього варіанта і викличте `mock_rule_create_from_entry`:
   - `match_body_fields=["/action"]` для POST-варіантів; для GET лишіть порожнім (додайте `match_query_fields`, якщо варіант обирає параметр query).
   - `mode="patch"` (за замовчуванням): відповідає справжній сервер; `response_patches` міняють указані поля відповіді, `request_patches` — тіло запиту, `request_headers` — його заголовки до відправки. Переважний варіант: дані лишаються свіжими.
   - `status` підміняє код відповіді в будь-якому режимі (`500`, `401`, `429`). Один код зі справжнім успішним тілом застосунок може не сприйняти за помилку; для правдоподібного збою беріть `mode="fixture"` з тілом помилки.
   - `delay_ms` затримує відповідь (0–60000 мс) — для перевірки лоадерів і тайм-аутів клієнта. Затримка діє лише на запити цього правила; `throttling` натомість сповільнює весь трафік Charles.
   - `request_headers` задає або замінює заголовок, а `null` видаляє його: `{"X-App-Version": "9.9.9", "X-Debug": null}`. `Host` і `Content-Length` тримає диспетчер, їхня правка відхиляється з попередженням. У режимі fixture ігноруються: на сервер нічого не йде.
   - `mode="fixture"`: віддається знята відповідь (правки застосовуються під час віддачі) з будь-яким `status`, без звернення до сервера — для помилок і роботи без сервера.
   - `host_scope="any"` (за замовчуванням) діє на всіх хостах маршруту; `"exact"` або `host="stage.example.com"` звужують. Правило для точного хоста перемагає загальне.
   - Не фіксуйте сегменти шляху, що залежать від платформи чи версії застосунку: `match_path="/api/*/payoneer"` покриває `/api/p24-aos2/payoneer` і його iOS-варіант. `*` замінює один сегмент або частину сегмента (`p24-*`), не перетинає `/` (`**` не має особливого змісту) і має покривати шлях зразка; якщо в сесії лише одна платформа, спитайте користувача, які сегменти змінюються.
   - Якщо запит підходить під кілька правил, перемагає правило з більшим `priority`, потім точний хост важливіший за шаблон, потім точний шлях важливіший за шаблон, потім більше умов. Тому правило з точним шляхом без умови за тілом поб'є правило `/api/*/payoneer` з умовою за `action`; щоб для цього шляху перемогло правило за `action`, задайте йому більший `priority`.
   - Повторне прохання для того самого варіанта **доповнює** його правило; правка того самого поля замінює попередню. `merge=false` замінює правило цілком.
   - Правки перевіряються на знятому запиті й відповіді; помилка означає невірний шлях — виправте його, не обходьте перевірку.
4. `mock_dispatcher(action="start")`.
5. Користувач повторює дії. Перевірка: `query_live_capture_entries(capture_id, path_contains=..., response_header_name="X-Charles-MCP-Rule")` — у заголовку id правила; `passthrough` означає, що правило не підійшло.
6. Повідомте, що замокано (варіант, поля, режим, область).
7. Наприкінці: `mock_rule_set_enabled(false)` або `mock_rule_remove`, потім `mock_dispatcher(action="stop")` (вимкне Map Remote, трафік піде на справжні сервери).

### 6.4 Правки JSON Pointer

| Задача | Правка |
|---|---|
| Замінити значення | `{"op": "set", "path": "/data/balance", "value": 0}` |
| Додати ключ | `{"op": "set", "path": "/data/newFlag", "value": true}` |
| Змінити елемент масиву із заданим значенням поля | `{"op": "set", "path": "/data/balanceList/[currency=USD]/balance", "value": "1000.00"}` |
| Замінити елемент масиву за позицією | `{"op": "set", "path": "/data/items/0/status", "value": "blocked"}` |
| Додати в кінець масиву | `{"op": "set", "path": "/data/items/-", "value": {...}}` |
| Видалити ключ або елемент | `{"op": "remove", "path": "/data/banner"}` |
| Замінити тіло цілком | `{"op": "set", "path": "", "value": {...}}` |

**Обирайте елементи масиву за полем, а не за індексом**, особливо в правилах patch: сервер часто віддає списки (баланси, картки, рахунки) щоразу в іншому порядку, і `/balanceList/1` править не той елемент. Сегмент `[поле=значення]` обирає єдиний елемент, у якого поле дорівнює значенню; рядки порівнюються як є, числа і логічні значення — за JSON-значенням (`[id=42]`, `[balance=0]` збігається з `0.0`, `[active=true]`). Символ `/` у значенні екранується як `~1`, як у будь-якому JSON Pointer (`[path=~1api]` для `/api`), а `~` — як `~0`. Якщо збігу немає або їх кілька, правка не застосовується (`X-Charles-MCP-Warning`), а не міняє чужий елемент. Беріть поле, яке однозначно визначає елемент.

Ключі з `/` або `~` екрануються як `~1` і `~0`. Проміжні об'єкти не створюються автоматично. Form-тіла (`application/x-www-form-urlencoded`) правляться як плоскі об'єкти: `{"op": "set", "path": "/lang", "value": "en"}`.

### 6.5 Зберігайте контракт знятої відповіді

Деякі застосунки розбирають відповідь суворіше за будь-яку JSON-бібліотеку: переставлений об'єкт, зникла обгортка або число, що з `0.0` стало `0`, дають загальний екран «сервер недоступний», хоча мок відповів 200. Порядок ключів у JSON нічого не означає, але фікстуру все одно варто тримати настільки близькою до знятої відповіді, наскільки дозволяють інструменти.

1. **Починайте зі справжнього запису**, а не з пам'яті: `get_traffic_entry_detail(..., include_full_body=true)`, збільшуючи `max_body_chars`, доки тіло не буде повним. Обрізане preview ховає саме той хвіст, де форма і ламається.
2. **Будуйте фікстуру з цього запису** — `mock_rule_create_from_entry(mode="fixture")` або `mock_create_from_entry` — і міняйте правками лише названі поля. Обидва інструменти зберігають порядок ключів, назви полів, порядок масивів і скалярні типи (`0` лишається цілим, `0.0` — дробовим), але JSON вони пересеріалізовують: змінюються відступи, у кінці додається новий рядок, `1.50` стає `1.5`, `\u0421` — самим символом, а дублі ключів схлопуються. Якщо застосунку потрібні вихідні байти, пишіть їх через `mock_rule_write(fixture_text=...)` або правте створений файл `<rule_id>.body`.
3. **Зберігайте заголовки, які читає застосунок**, насамперед `Content-Type` разом із charset; правило, створене із запису, копіює знятий. Транспортні заголовки диспетчер веде сам і переписує в кожній відповіді: `Content-Length`, `Content-Encoding` (тіла доходять до застосунку вже розпакованими), `Date`, `Server` і власний `X-Charles-MCP-Rule`. Вони не є частиною контракту застосунку.
4. **Звіряйтеся зі справжньою відповіддю.** Коли застосунок повторить запит, порівняйте новий запис із вихідним через `get_traffic_entry_detail(include_full_body=true)`: заголовок правила, статус, content type, форму верхнього рівня, порядок масивів і скалярні типи. Сам по собі HTTP 200 доводить лише те, що хтось відповів.

### 6.6 Інші рецепти для QA

- **Екран помилки**: правило fixture зі `status=500` (або 401, 404) для цього варіанта.
- **Порожній стан**: `{"op": "set", "path": "/data/items", "value": []}`.
- **Повільна відповідь одного ендпоінта**: `delay_ms=5000` у правилі — перевірка лоадерів і тайм-аутів.
- **Повільна мережа цілком**: `throttling("3G")` — діє на весь трафік Charles.
- **Перевірка аналітики**: `query_live_capture_entries(host_contains=<трекер>, request_body_contains=<подія>)`.

## 7. Перезапуски Charles

Перезапуск потрібен лише для додавання правила Charles для нового хоста або домену; файли моків, правила диспетчера і вмикання/вимикання інструментів його не потребують. Інструменти самі Charles не закривають і не запускають. Разом з користувачем:

1. Попросіть зберегти сесію, якщо потрібно, і закрити Charles (або, за явної згоди, закрийте його через `http://control.charles/quit`).
2. Попросіть **не відкривати Charles**, доки ви не повідомите, що правило записане.
3. Викличте `mock_route_setup(..., apply=true)` або `mock_setup_host(..., apply=true)`. Конфіг копіюється в каталог стану charles-mcp (у ньому ліцензійний ключ Charles і облікові дані Web Interface).
4. Попросіть запустити Charles — правило завантажиться.

Якщо перезапуск небажаний, дайте кроки для ручного налаштування в UI (`apply=false`): вони діють одразу після **Done** — Cancel їх скасовує.

Правило Map Remote, яке `mock_route_setup` записує або диктує:

| Поле | Значення |
|---|---|
| From | Protocol `https`, Host `*.example.com` (або один хост), Port `443`, Path `/api/*` |
| To | Protocol `http`, Host `127.0.0.1`, Port `18080` (`CHARLES_DISPATCHER_PORT`), Path **порожньо** — тоді Charles зберігає вихідний шлях |
| Preserve host header | **увімкнено** — диспетчеру потрібен вихідний `Host`, щоб обрати маршрут і правила |

Перевірено на Charles 5.2.1: шаблон хоста ловить піддомени, шлях доходить до диспетчера без змін, запити поза шаблоном шляху не мапляться. Імпорт XML-файлу у вікні Map Remote у Charles 5.2.1 не працює — не пропонуйте його.

## 8. Діагностика

| Симптом | Причина |
|---|---|
| Немає заголовка `X-Charles-MCP-Rule` | Map Remote вимкнений (запустіть диспетчер), правило в Charles не збережене (Cancel замість Done), не збіглися хост/шлях/протокол, немає SSL Proxying |
| Charles відповідає 503 «Name lookup failed» | Map Remote не застосувався, Charles пішов на вихідний хост |
| `passthrough` | Запит дійшов до диспетчера, але правило не підійшло: шлях, метод, значення `action`, вимкнене правило |
| 421 від диспетчера | Хост або шлях не покритий маршрутом — `mock_route_setup` |
| 502 від диспетчера | Сервер недоступний: мережа/VPN, тайм-аут, сертифікат (`verify_tls`) |
| Усі запити до домену падають | Map Remote увімкнений, диспетчер не запущений |
| `X-Charles-MCP-Warning` | Правка не застосувалася (тіло не JSON, шлях не знайдено); відповідь віддана без неї |
| Значення в застосунку не змінилося | Застосунок може кешувати: попросіть оновити екран або перезапустити застосунок; перевірте, що правило спрацювало |
| Вивантаження повільне або падає за тайм-аутом | Сесія завелика: очистіть її, вимкніть запис проксі macOS, звузьте через `host_contains` |
| Правка конфіга «зникла» | Її записали при запущеному Charles; повторіть за розділом 7 |

## 9. Обмеження

- Map Local: завжди 200; query і метод ігноруються.
- Диспетчер: WebSocket не підтримується; завантаження буферизуються цілком; стиснуті gzip тіла запитів не розбираються; JSON `true` не дорівнює form-рядку `"true"` під час зіставлення; шляхи порівнюються точно, якщо в правилі немає `*` (`/users/1` ≠ `/users/2`).
- Тайм-аут або обрив з'єднання не імітуються: є лише `delay_ms` і код відповіді.
- Одночасно лише одне live-захоплення.

## 10. Як повідомляти користувачу

Скажіть, що ви дивилися (захоплення, фільтри), що змінили (варіант, поля, режим, область), як перевірили (заголовок, статус), що лишилося ввімкненим (правила, диспетчер, правила Charles) і що користувачу робити далі. Не вставляйте сирі токени і повні номери карток.
